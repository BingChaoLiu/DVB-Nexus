\# DVB 数字沙盘与码流可视化分析平台 — 软件规格说明书（Spec v0.3 / 演练场全功能版）



> \*\*文档目的\*\*：本文档面向架构评审、核心开发与外部技术顾问（如 Claude / Gemini），全面整合“实时排查”与“互动式协议演练沙盘”双核心能力，并内置高级故障靶场案例库，用于对齐系统边界、仿真引擎架构、教学模块职责与实施路线。



\---



\## 1. 背景与愿景演进



传统的 DVB 接收链路故障定位长期依赖命令行工具（`dvbsnoop`、`TSDuck` CLI）与零散日志。工程师面对的问题不仅是“底层数据不可见”，更存在严重的\*\*工程人才断层痛点\*\*：标准文档晦涩、软硬件耦合深、初级工程师上手周期长（动辄需要数月甚至数年摸清整条链路）。



\*\*Spec v0.3 的核心战略定位\*\*：

本项目不仅是一个面向生产环境的\*\*实时码流排查利器\*\*，更是一个集成了“数字沙盘（Digital Sandbox）”与“协议演练场（Training Lab）”的综合性工程平台。通过支持“无硬件/无直播源”的虚拟流仿真、交互式拓扑拼装与故障靶场演练，让初级工程师在“玩中学、练中悟”，将底层 ETSI 标准内化为直观的链路因果直觉。

\## 2. 核心目标与验收标准



\### 2.1 目标（In Scope）



| ID | 目标 | 验收标准 |

| --- | --- | --- |

| G1 | \*\*双模运行能力\*\*：支持“实况流接入模式”（Live Mode）与“数字沙盘仿真模式”（Sandbox Mode） | 仿真模式下可完全脱离真实硬件/TS 文件自主生成合规链路状态 |

| G2 | \*\*交互式拓扑编排\*\*：前端自由组合 LNB → DiSEqC 开关 → Tuner → Demux → T2MI/BISS 链路 | 拓扑变更后，后端实时计算物理/逻辑状态并完成前端拓扑重绘 |

| G3 | \*\*沉浸式学习反馈\*\*：节点与协议字段绑定动态知识卡片、错误归因与标准引用 | 点击任意协议节点或异常状态，侧栏展示白话解析与 ETSI 标准出处 |

| G4 | \*\*故障靶场与注入\*\*：预置经典故障场景（如 BISS 密钥错位、T2MI 内层无 PAT、DiSEqC 冲突） | 学员可通过调整参数或修复配置使链路恢复绿色正常状态 |

| G5 | \*\*双流联动对照\*\*：支持传统 CLI 终端输出与图形化拓扑的实时对照 | 模拟 `tsp` 命令行输出与可视化节点状态 1:1 同步 |



\### 2.2 非目标（Out of Scope，v1）



\* 不做完整的 DVB 协议栈重实现（实况模式下复用 TSDuck/libdvbcsa/libdvbv5）；

\* 不做多用户云端隔离部署（v1 聚焦单机本地应用与本地实验沙盘）；

\* 不做视频内容 AI 质量评估。

\## 3. 用户与典型场景



\*\*主要用户\*\*：



1\. \*\*资深工程师/运维\*\*：用于生产环境的实时链路监测、射频故障排查、T2MI/BISS 证据链还原。

2\. \*\*初级工程师/新员工\*\*：用于无风险的协议学习、拓扑实验、故障排查直觉训练。



\*\*典型场景\*\*：



\* \*\*场景 S1（新人自主实验）\*\*：新人入职后启动沙盘模式，拖入 LNB 和 DiSEqC 开关，故意制造 13V 电压与高频段命令冲突，观察系统弹出的物理约束警告。

\* \*\*场景 S2（T2MI 故障辨析演练）\*\*：加载“内层 TS 缺 PAT”的预置靶场，通过三级子图展开（T2-MI Packet → BBFrame → Inner TS），学习区分“封装故障”与“复用器配置错误”。

\* \*\*场景 S3（BISS 密钥排查）\*\*：在沙盘中输入错误的 BISS 密钥，观察“PES 起始码校验失败”的证据链高亮，并阅读对应的排查提示。

\## 5. 核心功能模块规格



\### 5.1 交互式拓扑沙盘（Simulation Sandbox \& Component Palette）



允许用户在画布上自由拖拽和组装接收链路：



\* \*\*射频组件\*\*：Universal/Single LNB、DiSEqC 1.0/1.1 开关矩阵、Tuner/Demodulator。

\* \*\*传输与解密组件\*\*：T2MI 封装器、BISS 加扰/解扰器、Demux 分流器。

\* \*\*参数面板\*\*：点击任意组件可配置其内部参数（如本振频率、DiSEqC 端口、BISS 密钥、T2MI BBHEADER 属性）。



\### 5.2 沉浸式协议知识库与错因归因（Contextual Knowledge \& Hints）



\* \*\*节点白话解析\*\*：点击任何节点（如 DiSEqC、BISS、BBFrame），侧栏提供“标准背景、工作原理、ETSI 规范引用”。

\* \*\*智能错误归因\*\*：当链路出现 `warn` 或 `error` 时（如 BISS 解密失败、T2MI 校验错），系统自动展示结构化的排查指引与建议修复操作。



\### 5.3 故障靶场与闯关模式（Fault Injection \& Lab Mode）



\* \*\*预置实验包（Lab Packs）\*\*：系统内置多套经典故障关卡（如“DiSEqC 冲突排查”、“T2MI 封装畸变”、“BISS 密钥错位”）。

\* \*\*通关评测\*\*：初级工程师通过修改沙盘参数或修复配置，使拓扑全链路恢复“绿色（ok）”状态即视为通关。



\### 5.4 双流对照与 CLI 终端仿真（Dual-View CLI Bridge）



\* 在界面底部或分屏区域提供一个\*\*虚拟终端窗口\*\*，实时打印与当前拓扑状态对应的传统工具日志（如 `tsp -I dvb ... -P t2mi ...` 的输出文本）。让初级工程师无缝建立“命令行参数 ⇄ 图形化节点”的对应直觉。

\## 7. 附录：数字沙盘高级故障靶场案例库（Scenario Library）



\### 领域 A：射频与前端供电链路（RF \& Frontend）



\#### 案例 A1：Unicable (EN 50494 / EN 50607) 频道槽位冲突



\* \*\*现象描述\*\*：多 tuner 共享单根同轴电缆时，切换到特定高清频道提示“Tuner 锁定失败（No Lock）”，而其他频道正常。

\* \*\*底层根因\*\*：两个虚拟/物理 Tuner 被分配了相同的 \*\*SCR（Subscriber Channel Radio）槽位频率\*\*（例如均占用 1210 MHz），导致下发单向 DiSEqC 调谐指令时发生本振频率冲突。

\* \*\*沙盘训练目标\*\*：学习单线多路（Unicable）频段分配规则，观察 Tuner 节点配置面板中的槽位冲突告警，理解用户端频点与中频（IF）的映射关系。



\#### 案例 A2：22kHz 持续音调残留引起的低频段误码



\* \*\*现象描述\*\*：高频段（High Band）信道接收正常，但切换至低频段（Low Band）时，BER（误码率）急剧飙升，画面马赛克严重。

\* \*\*底层根因\*\*：LNB 供电电路或 Multiswitch 开关异常，本应用 0Hz（关闭 22kHz）的低频段指令中混入了残留的 22kHz 调制音调，导致 LNB 错误切入高频段本振（9.75GHz 错判为 10.6GHz）。

\* \*\*沙盘训练目标\*\*：观察物理视图中 LNB 电压（13/18V）与 22kHz 音调状态的组合逻辑，学习如何通过物理层状态排查硬件控制信号异常。



\---



\### 领域 B：多流、封装与嵌套层（Multistream \& T2MI）



\#### 案例 B1：T2MI PLP ID 映射错位



\* \*\*现象描述\*\*：外层 TS 锁定时钟正常，T2MI 封装节点指示灯为绿色，但内层 TS 节点的 Demux PID 树为空，无任何视频/音频业务输出。

\* \*\*底层根因\*\*：物理地面/卫星信道包含多个 PLP（Physical Layer Pipe，例如 PLP 0 传输数据，PLP 1 传输本地 TV 业务），但前端 Demux/PLP 分流器错误地锁定了数据流 PLP 0。

\* \*\*沙盘训练目标\*\*：展开 T2MI 三级子图（外层 TS Packet → BBFrame → Inner TS），学习多流环境下的 PLP / ISI 选择机制，理解“物理层锁定”与“逻辑流解析”的分层解耦。



\#### 案例 B2：BBHEADER 帧同步错位与 CRC 校验超阈值



\* \*\*现象描述\*\*：T2MI 节点频繁闪烁黄色警告，包计数器正常，但 BBFrame 解封装层持续出现 CRC 错误。

\* \*\*底层根因\*\*：上游复用器（Multiplexer）输出的 T2MI 封装帧中，BBHEADER 的长度字段或同步字节（SYNCD）由于传输抖动发生错位，导致后续 FEC 块解析边界紊乱。

\* \*\*沙盘训练目标\*\*：观察 T2MI 节点的 detail 面板中的 BBHEADER 校验状态，学习 ETSI TS 102 773 标准中帧头同步机制与错误传播路径。



\---



\### 领域 C：加扰、解密与条件接收层（BISS \& CA）



\#### 案例 C1：BISS Mode E 动态注入字（Injected ID）不匹配



\* \*\*现象描述\*\*：输入了从运营方获取的 16 字节 BISS 密钥，但 BISS 解密节点仍然报错：`PES Start Code Valid: Failed`，解密后输出为纯乱码。

\* \*\*底层根因\*\*：该流采用的是 \*\*BISS Mode E\*\* 加密，除了基础密钥（Session Word）外，还包含一个动态的注入私有数据（Injected ID / Buried ID）。用户误将其当作标准的 BISS Mode 1 进行解密。

\* \*\*沙盘训练目标\*\*：掌握 BISS Mode 1 与 Mode E 的底层密钥结构差异，通过沙盘的“双流对照证据链”（解密前后十六进制对比）识别加扰算法变体。



\#### 案例 C2：PID 映射混淆导致的条件接收（CA）字错配



\* \*\*现象描述\*\*：画面呈马赛克花屏或周期性黑屏，BISS 状态在 `clear` 和 `scrambled` 之间剧烈跳变。

\* \*\*底层根因\*\*：加扰 PES 流的 PID 在 PMT（节目映射表）中被动态更改，但解密器的 PID 过滤表（Demux Filter）未及时同步更新，导致 ECM（群控信息）与加密 PES 流错位。

\* \*\*沙盘训练目标\*\*：学习 SI/PSI 表（PAT/PMT/ECM）与解扰引擎的联动关系，通过 PID 树的时间轴标记定位状态跳变的根因。



\---



\### 领域 D：网络重构与 FastScan 扫描层（SI/PSI \& FastScan）



\#### 案例 D1：FastScan 后 NIT（网络信息表）版本不同步



\* \*\*现象描述\*\*：运营商在后台更新了 transponder 频点列表（例如调整了某个省份的频率），终端执行 FastScan 后，部分新频道仍无法播放。

\* \*\*底层根因\*\*：前端本地缓存了旧版 NIT（`table\_id\_extension` 版本号未变），或运营商在更新 NIT 时未同步更新 TSID（传输流 ID），导致 FastScan 扫描引擎直接命中了本地陈旧的缓存数据。

\* \*\*沙盘训练目标\*\*：观察 FastScan 面板的扫描进度、LC（Logical Channel）映射以及 NIT 表版本号比对机制，理解运营商前端数据下发与终端缓存的交互逻辑。



\#### 案例 D2：PCR 抖动（Jitter）超标引起的连续性计数器（CC）异常



\* \*\*现象描述\*\*：视频流码率在 15\~20 Mbps 波动，画面每隔几分钟出现无规律的卡顿，边指标（Edge Metrics）显示 CC（Continuity Counter）错误率持续缓慢上升。

\* \*\*底层根因\*\*：上游转码器输出的 PCR（节目时钟参考）间隔严重违反 ISO/IEC 13818-1 标准（Jitter > 500ms），导致解码器硬件缓冲区的同步锁相环（PLL）失锁，触发丢包保护。

\* \*\*沙盘训练目标\*\*：在边详情下钻视图中观察 PCR 抖动曲线与 CC 错误的关联性，培养对传输层时序健康的评估能力。

\## 8. 实施路线图



\### Phase 1 — 沙盘骨架与虚拟仿真 MVP（学习优先）



\* 实现前端拓扑拖拽画布与后端拓扑求值引擎；

\* 实现基础射频链（LNB → Tuner）与 Demux/PID 树的虚拟流生成；

\* \*\*验收\*\*：无硬件环境下，学员可在本地拖拽组件并完成基础链路仿真。

\* 对接 TSDuck 实况输入，打通 Live Mode；

\* 实现 T2MI 三级子图展开与 BISS 证据链校验；

\* 上线 CLI/UI 双流对照终端。

\* \*\*验收\*\*：支持真实 TS 文件与 DVB 接收卡实况接入。



\### Phase 3 — 闭环控制与靶场扩展



\* 实现反向控制 API（DiSEqC 下发、BISS 动态密钥加载）；

\* 扩展更多高级故障靶场；

\* 引入时序指标存储与回放功能。

\* \*\*验收\*\*：形成“学习训练 ➔ 实战排查”的完整闭环。

\## 9. 风险与开放问题



| ID | 风险/问题 | 影响 | 缓解 |

| --- | --- | --- | --- |

| R1 | TSDuck 对 T2MI 内部 BBHEADER 细节暴露不足 | G3 粒度受限 | Phase 2 评估 Rust `dvb-t2mi` 替补 |

| R2 | Multistream PLP 过滤在驱动层，TSDuck 可能无法精细控制 | G5 受限 | 与驱动/frontend 能力对齐，必要时降级为只读展示 |

| R3 | DiSEqC 命令回执依赖 `FE\_HAS\_LOCK`，非直接 ACK | 状态确认不精确 | 文档标注"推断结果"，多命令时序联合判定 |

| R4 | BISS 密钥安全 | 合规风险 | 内存驻留 + TLS + 日志脱敏 |

| R5 | 单机 Linux 限制 | 用户面窄 | v1 明确边界，v2 评估 Windows/macOS（DVB 设备驱动差异） |
